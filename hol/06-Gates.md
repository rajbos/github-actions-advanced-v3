# 🔨 Lab 6: Which gate is blocking?

**Time:** 35 minutes, plus policy setup. **Prerequisite:** [Lab 5](05-Stacks-and-queue.md), your own disposable organization-owned repository, and repository administrator access for required checks, environments and deployments. **ORG ADMIN OR EQUIVALENT REQUIRED:** the centrally required-workflow scenario additionally needs organization ruleset-management permissions. Repository admin access alone is not enough for that scenario. **GHEC REQUIRED:** the centrally required-workflow rule needs an eligible GitHub Enterprise Cloud organization and a workflow source repository with Actions sharing enabled for the intended organization. Record the source repository's current **Settings → Actions → General → Access** setting; do not broaden access without its owner's approval. There are **no administrator-prepared rulesets**: you create your own during this lab. **EMU SETUP / GHE.COM SETUP:** use your approved identity and actual enterprise host. If you lack the permissions or feature, use the instructor's recorded evidence for that part; do not request broader access or edit a shared rule to work around it. Real cloud resources are not part of this exercise.

## Objectives

Diagnose required checks, deployments and centrally required workflows independently without bypassing any gate.

Follow the organization's normal approval process. If participants lack technical permissions **or organization policy does not permit these changes**, the trainer may demonstrate the central-workflow portion instead; participants can still perform approved repository-local gate scenarios. The trainer also needs the required roles and explicit authorization, and must use a disposable demo repository. Create a uniquely named demo ruleset, choose **Only selected repositories**, and select **exactly that demo repository**, with only its default branch targeted. Show the saved selection before activation. Never target all repositories, broad patterns or participants' repositories for the demo. Learners predict and explain outcomes while the trainer operates the rule. Restore the demo's original sharing setting and remove only its course rule during cleanup. If a trainer demonstration is not authorized or technically available, use recorded evidence and state that live enforcement was not demonstrated. Do not request elevated access or an exception merely to finish the exercise.

## Prepare repository-local gates

1. Record your exact `OWNER/REPOSITORY`, its default branch, existing rules and a unique ruleset name, such as `actions-lab6-<repository>-<your-handle>-<date>-<suffix>`. Do not reuse another participant's ruleset.
2. Before enforcing anything, copy the three `06-*.yml` starters into `.github/workflows` and complete their TODOs. In `06-gates.yml`, keep the supplied detector/application jobs and always-running gate; implement explicit evaluation of detection success, impact decision and applicable result, rejecting missing/failed/cancelled/unknown evidence. In `06-staging.yml`, validate the boolean failure fixture, run the built local server with bounded `/health` checking and guaranteed normal-exit cleanup; only report success after healthy JSON. In `06-central-required.yml`, validate PR title nonemptiness and a 120-character limit using environment values, safely handling merge-group events without PR metadata. Replace intentional incomplete-step failures only with these checks. Review the implementation and lockfile before pushing to your default branch. Do not activate rules against unfinished starters. [Job conditions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idif), [environment deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), [Python environment access](https://docs.python.org/3/library/os.html#os.environ)

   The detector reuses `tj-actions/changed-files`, introduced in Lab 3, rather than a custom script. Its `base_sha` selects the merge-group base or PR base; `sha` selects the combined revision GitHub is testing. Full checkout history and `skip_initial_fetch` allow a local Git comparison without stored credentials or PR-list API permissions. The file patterns select everything except Markdown outside `.github/`. Their order matters: the final `.github/**` includes policy Markdown again. `all_changed_and_modified_files_count` includes deletions and file-type changes; zero selected files gives `checks=false`, otherwise `checks=true`. Counting both sides of renames prevents a code-to-Markdown rename from hiding removed code. A missing count conservatively requests checks; a failed action still fails detection and must fail the final gate. Keep `fail_on_initial_diff_error` enabled: a failed comparison is not "no changes". Review/lock the action reference before activation. [Changed-files inputs, patterns and outputs](https://github.com/tj-actions/changed-files/tree/v47.0.6)
3. In **your repository's Settings → Environments**, create course-only environment `lab-staging`. It runs a local server only; do not configure cloud credentials or a production target.
4. In **your repository's Settings → Rules → Rulesets**, create a branch ruleset, initially **Disabled**, with only your exact default branch included and no bypass actors. Record its ID. Start with **Require status checks to pass**, selecting the observed `required` check from GitHub Actions after your first disposable PR run. Activate it and confirm its effective branch rules.
5. Test the deployment scenario with a separate repository-local rule, **Require deployments to succeed**, selecting `lab-staging`. Disable your course-created check rule while isolating the deployment requirement. Repository environments belong to a repository: do not assume the same deployment requirement can be configured on an organization ruleset.

## Prepare the centrally required workflow, if eligible

### Authorize and configure source-workflow access

1. Identify the **workflow source repository**, which may be your own eligible participant repository, and the **protected target repository**, which must be only your participant repository. Record both exact names and the source's current **Settings → Actions → General → Access** setting. These are separate scopes even when the names are the same.
2. Before changing anything, obtain explicit owner/policy-owner approval for the intended source sharing and single-target organization rule. The sharing change needs repository-administrator access (subject to organization/enterprise restrictions); the central rule separately needs organization-owner or equivalent ruleset-management permission. If either approval or role is absent, use the authorized trainer alternative above.
3. If the source already permits the required access, leave that setting unchanged. Otherwise, **only after approval**, open the source repository's **Settings → Actions → General → Access**, select **Accessible from repositories in the organization** (wording may vary by visibility/host), and save. This can let other repositories in the organization use the source's actions and reusable workflows; it is not restricted to the one target selected by your ruleset. Review the [sharing guidance and access implications](https://docs.github.com/en/actions/how-tos/reuse-automations/share-with-your-organization) before approving it. Do not enable enterprise-wide access or change organization/enterprise policy to work around an unavailable setting.
4. Reopen the source setting and verify the saved access, then continue with the narrowly scoped rule below. If GitHub still rejects the source, record its actual error and stop that scenario; do not broaden access further. Record the original setting and the person responsible for restoring it.

### Create the single-target organization rule

1. In your **organization's Settings**, open **Repository → Rulesets → New ruleset → New branch ruleset**. Enter a unique course-only name and leave enforcement **Disabled**. [Create organization rulesets](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/creating-rulesets-for-repositories-in-your-organization)
2. Under **Target repositories**, choose **Only selected repositories** and select **exactly your participant repository**. Never select all repositories, a name pattern, a property filter or another participant's repository. Include only your exact default branch and leave the bypass list empty.
3. Select **Require workflows to pass before merging**, your eligible source repository, its default-branch ref and `.github/workflows/06-central-required.yml`. Your participant repository can be the source if eligible. Choosing the source workflow does **not** choose the repositories protected by the rule. If GitHub reports that Actions sharing is disabled, record the prerequisite as blocked unless the repository owner approves a temporary change; do not silently broaden access.
4. Save Disabled, reopen and verify its unique name, one selected repository, target branch and source workflow before activating it. **Evaluate** does not block merging. Disable the course-only deployment rule while testing this independent requirement. Existing shared rules must remain untouched.

Existing organization or enterprise rules still apply. Your new rule cannot weaken them. If a separate rule blocks your PR, identify it; do not modify it or add a bypass.
